A space is an isolated IdentityServer environment within one application deployment. Each space has its own configuration
and operational data, while the application shares the same process, code and database infrastructure.

Use Spaces when you need to host multiple security domains without operating a separate IdentityServer deployment for
each one. Examples include software-as-a-service tenants, regional environments or independently administered business
units.

## How Spaces Isolate Data

Spaces build on the pooled storage model in
[Duende Storage](/identityserver/data/providers/duende-storage/index.mdx). Each space maps to a storage pool, a logical
partition within the same database identified by a numeric pool ID. This isolates all configuration and operational data
for that space. IdentityServer resolves the current space at the start of a request and routes all subsequent store
operations to that pool.

The reserved management pool is separate from every pool that holds IdentityServer data. It stores each space definition,
including its matching rules and assigned data pool. The default space uses data pool `0`, while configured spaces normally
use positive pool IDs. Normal IdentityServer requests never use the management pool as their data pool.

```mermaid
flowchart LR
    admin["ISpaceAdmin"] --> management["Reserved management pool"]
    management --> definitionA["Space A definition"]
    management --> definitionB["Space B definition"]
    default["Default space"] --> pool0["Data pool 0"]
    definitionA --> pool1["Data pool 1"]
    definitionB --> pool2["Data pool 2"]
```

Use `ISpaceAdmin` from a protected administration path to create spaces or change their pool assignments. Moving a space
to another pool changes which data it sees, so authorize and audit these operations as changes to a security boundary.
Reserve pool reassignment and deletion for break-glass or deliberate deprovisioning procedures.

### Space Lifecycle: Delete, Undelete, and Purge

`ISpaceAdmin` manages the end of a space's life, through delete, undelete, and purge operations. Each method returns a
`SaveResult<SpaceId>`. Check its success state instead of assuming the call worked.

1. `DeleteAsync(SpaceId id, CancellationToken ct)` soft deletes the space. Its pool data is blocked from reads and
   writes but retained. The space's match patterns and pool ID stay reserved, so no other space can claim them.
   Deleting a space that is already deleted succeeds without changing anything. It fails with `not_found` for an
   unknown space and with `version_conflict` when the space was modified concurrently.
2. `UndeleteAsync(SpaceId id, CancellationToken ct)` restores a deleted space to active, along with its matching
   rules. Calling it on a space that is already active succeeds without changing anything.
3. `PurgeAsync(SpaceId id, CancellationToken ct)` permanently removes the space. It purges all data in the space's
   storage pool and then deletes the space record. A purge can't be undone. It's also the only step that releases the
   space's match patterns and pool ID for reuse.

`PurgeAsync` is only valid for a space that you already deleted with `DeleteAsync`. Otherwise it returns a failed
result and doesn't throw:

| Situation                                              | Failure                                                                            |
|--------------------------------------------------------|------------------------------------------------------------------------------------|
| The space doesn't exist or is already purged           | `not_found`                                                                        |
| The space is still active                              | `validation_failed`, asking you to call `DeleteAsync` first. No data is removed.   |
| The space uses the reserved Default or Management pool | `validation_failed`. No data is removed.                                           |
| Purging failed in one or more storage instances        | `purge_incomplete`. The space record is kept, so call `PurgeAsync` again to retry. |
| The space was modified concurrently                    | `version_conflict`. The pool data may already be removed.                          |

`PurgeAsync` purges the space's pool from every registered storage instance. If any instance fails, it returns
`purge_incomplete` and keeps the deleted space record, match patterns, and pool ID reserved so the operation can be
retried. Data may already have been removed from instances that succeeded.

#### Undelete Failures

`UndeleteAsync` returns a failed result and leaves the space deleted in these cases:

| Error code          | Cause                                                                                                                                                                                          |
|---------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `eav_conflict`      | Another space has claimed a unique extended property value that the deleted space held. You get one error per conflicting value, naming the attribute, the value, and the space that holds it. |
| `schema_drift`      | The current schema no longer has an attribute that the deleted space stored. You get one error per missing attribute.                                                                          |
| `validation_failed` | Another space now uses one of the space's origins with a different path configuration (with a path where the deleted space has none, or the other way around).                                 |
| `version_conflict`  | The space was modified concurrently.                                                                                                                                                           |
| `not_found`         | The space was never created or has already been purged.                                                                                                                                        |

An undelete never partially restores a space. It either fully succeeds or leaves the space deleted.

Deleting a space releases its unique extended property values so other spaces can claim them. That's why a later
`UndeleteAsync` can fail with `eav_conflict`.

## How Spaces Resolve Incoming Requests

A space can match an incoming request by:

* Origin, such as `https://tenant.example.com`
* Path segment, such as `/acme` under the default `/t` prefix
* Both origin and path

Origin claims take precedence so a path cannot route a request away from a space that owns the host. With the default
prefix, a space whose path is `/acme` receives requests under `/t/acme`. Middleware moves `/t/acme` to `PathBase` before
ASP.NET Core routing, leaving the remaining path for IdentityServer endpoints.

Requests that explicitly use the space path prefix but do not match a space receive `404 Not Found`. By default, other
unmatched requests also receive `404 Not Found`; you can opt into the default space with `FallbackToDefault`.

:::caution
Only enable `FallbackToDefault` when serving an unmatched host or path from the default space is an intentional part of
your isolation model. A strict `404 Not Found` response is safer for multi-tenant deployments.
:::

:::caution[Leave `IssuerUri` unset with Spaces]
Spaces rely on IdentityServer inferring the issuer from each request's origin and path base, which is what gives every
space its own `iss` claim. Leave `IssuerUri` unset so each space has its own issuer. Setting a fixed value makes every
space return the same `issuer`/`iss`, although their data and normal OpenID Connect discovery endpoints remain separate.
See [Multi-Issuer](/identityserver/tokens/issuer.mdx#multi-issuer) for how issuer inference works.
:::

## UI and Application Services

Spaces use the same login, consent, logout and error page implementations. Space resolution runs before ASP.NET Core
routing and path-based resolution moves the matched prefix into `PathBase`. The shared UI routes therefore run within the
resolved space and read that space's configuration and operational stores.

Spaces do not add per-space UI code or branding. To vary UI behavior, inject `ISpaceContextAccessor` into a scoped UI
service, read the resolved `SpaceId` and load your own space-aware settings. Apply the same pattern to custom services that
need space-specific behavior.

Space resolution is independent of the `tenant:` value clients can send in `acr_values`. That value is an untrusted,
client-supplied hint that your login page can use within a space; it never selects a space. See
[Tenant Hints](/identityserver/ui/login/tenants.md#tenant-hints-versus-spaces) for a comparison.

Custom user stores, such as ASP.NET Identity or your own user database, and other application-level services are not
made space-aware automatically. You must isolate or partition them yourself when users, profile data, email delivery or
other dependencies belong to a specific space. Duende User Management is the exception: it works with Spaces out of the box,
and stores each space's users in that space's own database without extra configuration.

:::note[Duende User Management]
[Duende User Management](/identityserver/identity/user-management/index.mdx) uses the same storage factory as
IdentityServer. When Spaces is enabled, User Management data is routed to the resolved space's pool by default. This
isolates user profiles, authenticators, roles and groups per space.

If users must be shared across spaces, use a deliberately separate user directory architecture rather than the default
[space-aware User Management storage](/identityserver/data/providers/duende-storage/getting-started.md#use-duende-user-management).
:::

## Cookies and Space Paths

In a path-based space, IdentityServer sets the `Path` of its cookies to that space's path. For this to work, call
`UseSpaceResolution()` before `UseIdentityServer()`. Don't use a `__Host-` name for the cookies IdentityServer wraps,
because that prefix requires `Path=/` (see [Using the __Host- Prefix](#using-the-__host--prefix)).

The cookie `Path` is IdentityServer's base path on each request, which is the hosting `PathBase` plus the matched space
path. For a space at `/space-a` hosted under `/host`, the path is `/host/space-a`. Spaces matched by origin only have no
space path, so their cookies use the hosting `PathBase`, or `/` when it is empty.

`UseIdentityServer()` records the request's `PathBase` as the base path, and `UseSpaceResolution()` is what adds the
matched space path to `PathBase`. If space resolution runs after `UseIdentityServer()`, or not at all, the cookie path
is only the hosting `PathBase`, or `/` when it is empty.

### Why Cookies Are Scoped to the Path

Path-based spaces share one host name. If their cookies used `Path=/`, the browser would send each space's cookies to
every other space on that host, and all spaces would share a single session cookie. Signing in to space B would replace
the session cookie of space A. With `PartitionDataProtection` set to `false` and a self-contained session cookie, space
B could also accept the cookie from space A. With server-side sessions, the session is stored per space, so space B
can't find a session created in space A. Scoping the cookies to the space path gives each space its own cookies, so the
browser doesn't send one space's session to another space and one space's sign-in doesn't replace another's.

The same reasoning applies when you host IdentityServer under a `PathBase` without Spaces. Hosting under a path usually
means other applications share the host name. Scoping IdentityServer's cookies to its base path keeps browsers from
sending them to those applications, and avoids accidental collisions with cookies of the same name.

Path scoping isn't a security boundary. Any application on the same host can set a cookie with the same name and path,
and cookies scoped to a parent path are also sent to nested paths. Don't host untrusted applications on the same host
name as IdentityServer.

### Cookies Scoped to the Space Path

IdentityServer sets the space path on these cookies:

* The session cookie. It uses the `idsrv` scheme by default. If you set
  `IdentityServerOptions.Authentication.CookieAuthenticationScheme`, or rely on the default authenticate or default
  scheme, that scheme's cookie is used instead, for example ASP.NET Core Identity's `Identity.Application`.
* The `idsrv.external` cookie for external authentication.
* The temporary message cookies that carry state between pages, such as consent.
* The check-session cookie, `idsrv.session` by default.

The check-session cookie is only issued when `Endpoints.EnableCheckSessionEndpoint` is enabled. Its name comes from
`Authentication.CheckSessionCookieName`, and it keeps using `Domain` and `SameSite` from
`Authentication.CheckSessionCookieDomain` and `Authentication.CheckSessionCookieSameSiteMode`.

Your other application cookies, and the correlation and nonce cookies of external handlers such as OpenID Connect, are
not changed.

### Customizing the Session Cookie

For the session cookie, the `idsrv.external` cookie and the cookie of the configured scheme, IdentityServer replaces
`options.Cookie` on the cookie authentication options with a wrapper around your `CookieBuilder`. The wrapper passes
`Name`, `Domain`, `SameSite`, `HttpOnly`, `Secure` and your other settings through and replaces only `Path`. A `Path`
you set on `options.Cookie` is ignored for these cookies. Cookie extensions you add to the wrapper are copied into the
cookie it builds.

If your code assigns a new `CookieBuilder` to `options.Cookie` after IdentityServer has wrapped it, the new builder
isn't wrapped. IdentityServer then doesn't set the space path on that cookie.

### Using the __Host- Prefix

:::caution[Don't use the __Host- cookie name prefix with a non-root cookie path]
The `__Host-` prefix requires the cookie path to be `/`. IdentityServer checks the name of the session cookie, the
`idsrv.external` cookie and the cookie of the configured scheme. If the name starts with `__Host-` and the resolved
path for the request isn't `/`, IdentityServer throws an `InvalidOperationException` before it issues the cookie.
:::

You get this exception in any path-based space, because the cookie path is the space path. You also get it when the
hosting `PathBase` isn't empty, for example when IdentityServer runs under `/host`. That applies to origin-only spaces
and to apps that don't use Spaces at all. The message starts with:

```text
Cookie '<name>' uses the '__Host-' prefix, which requires the cookie path to be '/', but the resolved IdentityServer cookie path is '<path>'.
```

Use the `__Secure-` prefix instead. It still enforces `Secure` but permits non-root paths.

IdentityServer doesn't run this check for the check-session cookie or the message cookies. They get the same path as
the other cookies.

### Existing Cookies

IdentityServer doesn't migrate or remove existing cookies. Cookies issued with `Path=/` before IdentityServer scoped
cookies to the base path stay in the browser until they expire. Browsers still send them to every path, and they can
exist next to a new cookie with the same name. Changing the path alone doesn't end existing sessions. In a named space
with data protection partitioning enabled, an older cookie can't be read, so the user signs in again. Otherwise, the
older cookie can still be accepted. If existing sessions must end, end them explicitly, for example by changing the
session cookie name.

## What Spaces Does Not Isolate

:::caution[Spaces Do Not Isolate Every Process-Level Dependency]
Spaces isolate persisted data and, by default, [ASP.NET Core Data Protection](/general/data-protection.md) and keyed
`HybridCache` entries created through `IHybridCacheFactory`. They do not automatically isolate every process-level
dependency. Review signing credentials, external caches, telemetry, rate limits and custom services to decide whether
they also need space-aware configuration.

For example, sharing signing credentials reduces cryptographic separation between spaces. Token validation still checks
the issuer, audience and other constraints, but each space should use deliberately scoped credentials when your security
model requires independent trust boundaries. IdentityServer protects its own signing keys through the unpartitioned
Data Protection provider, so they remain valid across every space even when `PartitionDataProtection` is enabled.
:::

To inject the Spaces cache into an application service, use its service key:

```csharp
// CachedService.cs
using Duende.IdentityServer.Spaces;
using Microsoft.Extensions.Caching.Hybrid;
using Microsoft.Extensions.DependencyInjection;

public sealed class CachedService(
    [FromKeyedServices(SpacesServiceProviderKeys.SpacesCache)] HybridCache cache)
{
}
```

By default, Spaces partitions Data Protection by space: `SpacesOptions.PartitionDataProtection` is `true`, and a
protector obtained from the app's `IDataProtectionProvider` binds to the space resolved at the time you call `Protect`
or `Unprotect`. Data that must be shared across every space, such as IdentityServer's signing keys, uses
`IUnpartitionedDataProtectionSource.GetUnpartitioned()` (or the `GetUnpartitioned()` extension on
`IDataProtectionProvider`/`IDataProtector`) to opt out of partitioning for that specific protector. See
[Data Protection](/general/data-protection.md) for more on how providers and protectors work.

Your administration system must authorize operators for the specific spaces they manage. Never trust a space identifier
supplied by a client without allowing the resolution middleware to validate it against a configured match pattern.
