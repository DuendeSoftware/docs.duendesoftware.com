## Package Changes

The IdentityServer 8.1 preview includes User Management and Spaces in `Duende.IdentityServer`. Remove separate
package references for those features if present, and follow the [Spaces getting-started
guide](/identityserver/spaces/getting-started.mdx) and [User Management getting-started
guide](/identityserver/identity/user-management/getting-started.mdx) for package commands.

## Paging Result Property Rename

:::caution[Unreleased change after preview.7]
In product source after `8.1.0-preview.7`, `QueryResult<T>.HasPrevResults` has been renamed to
`HasPreviousResults`. The new name is not available in preview.7. When upgrading to a release that includes this
change, update and rebuild code that reads or sets the property, including
`Pages/ServerSideSessions/Index.cshtml` in projects generated from the Quickstart UI templates.

The default JSON property name also changes. If you serialize `QueryResult<T>`, update consumers and migrate persisted
data using the old name as needed. Custom serialization may differ.
:::

## User Management Authentication Changes From 8.0

### Password Defaults

`PasswordOptions.MinLength` changes from `8` to `15`. `MinLower`, `MinUpper`, `MinDigits`, and `MinSymbols` each
change from `2` to `0`; `MaxLength` remains `64`. Hosts without explicit password options therefore reject newly
set or changed passwords shorter than 15 characters, but no longer require a mixture of character types.

Existing stored passwords are not re-checked against the new composition or minimum-length rules on sign-in.
If every sign-in requires a second factor in addition to the password, you can set `MinLength` to `8`.

To retain the 8.0 defaults explicitly:

```csharp
// Program.cs
using Duende.IdentityServer;
using Duende.UserManagement;
using Duende.UserManagement.Authentication;

builder.Services
    .AddIdentityServer()
    .AddUserManagement(um => um
        .Authentication(auth => auth.Configure(options =>
        {
            options.Passwords.MinLength = 8;
            options.Passwords.MinLower = 2;
            options.Passwords.MinUpper = 2;
            options.Passwords.MinDigits = 2;
            options.Passwords.MinSymbols = 2;
        })));
```

See [Password Configuration](/identityserver/identity/user-management/authentication/passwords.mdx#configuration)
for the options and security considerations.

### Recovery Codes

Newly generated recovery codes contain 13 Crockford Base32 characters (65 bits of entropy), rather than 10
characters (50 bits). Existing 10-character codes, including imported codes, remain valid until used or replaced.
Generating a new set replaces the old set. No migration is needed, and the default count remains 10.
See [Recovery Code Generation](/identityserver/identity/user-management/authentication/recovery-codes.mdx#generation-flow).

### Email And SMS One-Time Password Defaults Are Unchanged

Email and SMS One-Time Passwords (OTPs) still contain 8 alphanumeric Crockford Base32 characters (40 bits of
entropy), expire after 5 minutes, allow a new code after 1 minute, and permit 4 verification attempts per code.
These are existing defaults, not an 8.1 behavior change. See
[OTP Defaults](/identityserver/identity/user-management/authentication/otp.mdx#what-user-management-does-for-you).

## Cookie Path Changes From 8.0

In the 8.1 preview, IdentityServer scopes its session cookie, `idsrv.external` cookie, and the cookie of the configured
authentication scheme to the request's IdentityServer base path. This affects applications hosted under a non-empty
`PathBase` even when they do not use Spaces. For example, an application hosted under `/identity` uses
`Path=/identity` instead of `/`. An explicit `Path` on `options.Cookie` is ignored for these wrapped cookies.

If one of these cookies uses a `__Host-` name and the resolved path is not `/`, issuing it throws an
`InvalidOperationException`. Use a `__Secure-` name instead when a non-root cookie path is required.

Existing `Path=/` cookies are not migrated or removed and can coexist with new same-name cookies scoped to the base
path. Changing the path alone does not end existing sessions. Review
[Existing Cookies](/identityserver/spaces/index.mdx#existing-cookies) before
deployment, including whether you need to end sessions explicitly. Cookie paths are not a security boundary.

## Server-Side Session Concurrency

IdentityServer 8.1 adds optimistic concurrency to server-side session updates. The Entity Framework operational store
requires a migration adding a non-null `Version` integer column to `ServerSideSessions`, with a default of `1`.
Generate and apply the migration with your operational-store context before deploying the 8.1 application:

```bash
dotnet ef migrations add Update_DuendeIdentityServer_v8_1_Sessions -c PersistedGrantDbContext -o Migrations/PersistedGrantDb
dotnet ef database update -c PersistedGrantDbContext
```

For SQL Server, the schema change is equivalent to:

```sql title="SQL Server"
ALTER TABLE [ServerSideSessions] ADD [Version] int NOT NULL DEFAULT (1);
```

For deployment, generate the script from your EF Core migration with
`dotnet ef migrations script -c PersistedGrantDbContext`. Use the database provider and table mapping configured by
your application rather than using the SQL Server example for other providers.

Without the migration, session reads and deletes fail because the `Version` column is missing, and new sign-ins do not
persist a server-side session. During a rolling deployment, older nodes do not enforce the version check. Complete the
rollout before relying on concurrency protection across the whole cluster.

Custom `IServerSideSessionStore` implementations must update their `UpdateSessionAsync` method to return `Task<bool>`.
They must atomically compare the submitted `Version` with the stored version, save and increment it only on a match,
and return `false` without writing when the session changed or was removed after it was read. A `Version` of `0` skips
the concurrency check; query results can also carry `0`, so it does not indicate whether the session was read. See the
[server-side session store reference](/identityserver/reference/v8/stores/server-side-sessions.mdx#concurrent-updates-in-identityserver-81).

## Key Management

`Caching.CacheLockTimeout` remains in IdentityServer 8.1 as an obsolete property. It has no effect with the default
distributed key manager, though the compatibility `KeyManager` still reads it if a host explicitly uses that legacy
implementation. Use `KeyManagement.KeyCreationLockTimeout` with the default key manager to configure the time to wait
for the signing-key creation lock. It defaults to 60 seconds and must be greater than zero. See
[Key Management](/identityserver/fundamentals/key-management.mdx#key-creation-across-nodes-identityserver-81-and-later).
