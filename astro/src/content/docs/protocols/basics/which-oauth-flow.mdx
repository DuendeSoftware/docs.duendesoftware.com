Use these grants:

* **Apps with users:** the authorization code flow with PKCE, for browser, native, and server-side apps alike.
* **Services acting for themselves:** the client credentials grant.
* **Devices with limited input:** the device authorization grant.
* **Never:** the password grant (resource owner password credentials, ROPC).
* **Avoid:** the implicit grant.

## Why the Choice of OAuth Flow Matters

A grant is the way a client gets an access token from the authorization server (AS). Three questions decide which one you use: is a user present, can the client keep a secret, and does the device have a keyboard or browser? The current security guidance rules out the password grant and discourages the implicit grant, because both put credentials or tokens in places where they leak.

## Choosing an OAuth Flow Step by Step

### 1. Pick by client type and user

A client is public when it cannot keep a secret and confidential when it can. Start with that, then match the grant to the situation.

* Browser or native app (public client): [authorization code with PKCE](/protocols/oauth-2x-core/pkce.mdx). A native app signs the user in through the system browser, an external user agent.
* Server-side web app (confidential client): authorization code, with client authentication at the token endpoint.
* Service acting for itself: [client credentials](/protocols/oauth-2x-core/client-credentials.mdx), for confidential clients only.
* Device with limited input: the [device flow](/protocols/oauth-2x-core/device-flow.mdx). The user signs in at the AS on another device, and the client should start it only when the user asks. It is not meant to replace browser-based OAuth on capable devices.

Credentials in a native app can be extracted, and a user can read those in a browser app, so both kinds of client are public.

<Cite k="clientType" />

### 2. Apply the rules at their levels

Once you have a candidate grant, check it against the current guidance. Four rules matter.

* PKCE: public clients must use it, and it is recommended for confidential clients. Use it for every authorization code flow. A confidential OpenID Connect client may use the ID token `nonce` instead, but PKCE covers more cases. The challenge must be bound to the client and user agent that started the request, by keeping the `code_verifier` in that browser session.
* Client credentials: only confidential clients may use it, the client must authenticate, and the AS should not include a refresh token.
* Password grant (resource owner password credentials, ROPC): must not be used.
* Implicit: should not be used unless access token injection is prevented and the leakage vectors are mitigated. Use the authorization code grant, which keeps tokens out of the browser URL.

<Cite k="bcpPkce" />

### 3. If a grant is disallowed, AS refuses

This is a failure branch. When the client picked a grant it is not allowed to use, the AS refuses it. The token endpoint returns `400` with `unauthorized_client` (RFC 6749 section 5.2) when an authenticated client uses a grant type it is not allowed to use. At the authorization endpoint the same error comes back as a redirect query parameter (section 4.1.2.1). Policy on which clients may use which grant is the AS's choice, so compare the error with the client's configured grant types.

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"unauthorized_client"}
```

## OAuth 2.1 Status

OAuth 2.1 (draft-ietf-oauth-v2-1-16) is still an Internet-Draft. It does not specify the implicit and resource owner password credentials grants. The client credentials rules come from RFC 6749, while the PKCE, password grant, and implicit rules come from RFC 9700.
