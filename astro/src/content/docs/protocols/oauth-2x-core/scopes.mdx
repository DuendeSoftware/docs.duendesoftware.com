The client asks for scopes at a resource. The AS may narrow the grant to what its policy allows, and the API still checks audience and its own rules.

## Why It Exists

A token that says only "reports.read" does not say which API it is for, and an API that trusts any such token accepts tokens meant for someone else. Two things fix that. The client asks for access with a scope, and names the target API with a resource. The authorization server (AS) may narrow what it grants, then the API checks the token's audience and applies its own rules. After reading, you can tell which of these three decisions belongs to configuration, token validation, and application code.

Two terms first. A **scope** is a named piece of requested access, such as `reports.read`. A **resource** is the URL of the target API. The token's `aud` (audience) claim records which API the token is for.

## How It Works

The browser carries steps 1 and 2 as redirects, and the client talks to the AS and API directly in the other steps. Steps 6 and 7 are two separate rejections, not a sequence. A call fails on the audience check or on the API's own policy.

## Step by Step

### 1. Client requests scopes at one resource

The client sends three scopes and one resource. Scope strings are defined by the AS, are case-sensitive, and are space-delimited. They are shown here percent-encoded. `resource` SHOULD be the most specific URI, and the AS may use it as the audience or map it to one (RFC 8707 section 2). Compare the request with the token you will see in step 4: the client asked for three scopes and got back one.

```http
GET /authorize?response_type=code&client_id=reports-app
  &state=af0ifjsldkj
  &redirect_uri=https%3A%2F%2Fapp.example%2Fcb
  &scope=reports.read%20reports.export%20admin.delete
  &resource=https%3A%2F%2Freports.example HTTP/1.1
Host: idsrv.example
```

<Cite k="rfc6749_3_3" />

### 2. AS redirects back with a code or error

The AS may narrow the grant, or reject the request with `invalid_scope`. How it decides is its own policy. One common model is a five-way intersection of what the client may ask for, what the user may have, what the user consented to, what the server offers, and what the resource supports. That is an implementation model, not RFC 6749 mechanics. A consent screen and store are one way to reach a decision, and the RFC says only that approval comes from asking the owner or from other means.

Both outcomes are redirects to the client with `state`, not requests to the AS. `invalid_target` is the RFC 8707 error for a resource that is invalid, missing, unknown, or malformed. An invalid combination of resource and scope is reported with `invalid_scope`. The code was issued for the narrowed grant, and the client already chose the resource in step 1.

```http
HTTP/1.1 302 Found
Location: https://app.example/cb
  ?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj
On error, instead:
Location: https://app.example/cb
  ?error=invalid_scope&state=af0ifjsldkj
```

<Cite k="authResp" />

### 3. Client redeems the code at the AS

The client sends the code straight to the token endpoint, over a back channel. `redirect_uri` is required here only because it was in the authorization request, and it must be identical. A public client must use PKCE (RFC 9700 section 2.1.1). The credential is base64 of `reports-app:s3cr3t`.

```http
POST /token HTTP/1.1
Host: idsrv.example
Authorization: Basic cmVwb3J0cy1hcHA6czNjcjN0
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
  &redirect_uri=https%3A%2F%2Fapp.example%2Fcb
```

<Cite k="tokenReq" />

### 4. AS returns a token with the narrowed scope

Compare `scope` in the response with the three scopes in step 1. The response must include `scope` because it differs from the request. The JWT `scope` claim carries the scope associated with the issued token, here the narrowed one, and `aud` limits the token to one API. This is the first .NET concern: the scopes your API accepts are configured in the AS, as API scopes. `expires_in` is only RECOMMENDED. Opaque or reference tokens are equally valid, and then the API uses a server-side lookup, for example introspection, instead of reading claims.

```http
HTTP/1.1 200 OK
Cache-Control: no-store
Pragma: no-cache

{"access_token":"eyJ...","token_type":"Bearer",
 "expires_in":300,"scope":"reports.read"}
Decoded JWT: aud = https://reports.example,
  scope = reports.read
```

<Cite k="rfc6749_5_1" />

### 5. Client calls the API with the token

The client sends the token as a Bearer credential. The API now has to decide whether to trust it, and the next two steps show two ways that fails. A JWT is validated through the API's own checks, and an opaque token through a server-side mechanism.

```http
GET /tenants/acme/reports/42 HTTP/1.1
Host: reports.example
Authorization: Bearer eyJ...
```

<Cite k="bearer" />

### 6. If aud is wrong, API returns 401

This is the second .NET concern: token audience validation. The API checks that its own identifier is in `aud`. In this failure the client holds a token for `https://files.example`, and it carries the `reports.read` scope string. The API must reject it anyway, because scope alone is not an audience restriction. The 401 is a SHOULD in RFC 6750 section 3.1, and the rejection itself is a MUST in RFC 9068 section 4. For the full validation pipeline, see [access token validation](/protocols/tokens/access-token-validation.mdx). Request and response are shown on one wire.

```text
Request carried a JWT: aud = https://files.example,
  scope = reports.read
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"
```

<Cite k="rfc9068_4" />

### 7. If policy fails, API returns 403

This is the third .NET concern: an application authorization policy. A token with the right audience and scope can still get `403`, because the tenant and ownership rule is the API's own decision. Here the token is valid, but the user is not in tenant `other`. RFC 9068 section 4 leaves the details of these checks beyond its scope. `insufficient_scope` is for a token whose scope is too low, which is not this case. Request and response are shown on one wire.

```text
Request: aud and scope valid, GET /tenants/other/reports/9
Application rule: this user is not in tenant other
HTTP/1.1 403 Forbidden
```

<Cite k="rfc9068_4" />

## Notes

The consent prompt and stored consent record are not RFC 6749 mechanics. The RFC says only that the AS authenticates the owner and obtains a decision by asking or by other means.

RFC 9700 section 2.3 lets scope or resource be used to determine the resource server, so scope can help pick the API. For a JWT access token the audience restriction still comes from `aud` (RFC 9068 section 4 requires the check). RFC 9700 section 2.3 says access tokens SHOULD be audience-restricted, and that the `aud` claim MAY be used for it.

On a refresh request, `scope` MUST NOT include any scope not originally granted (RFC 6749 section 6). For `resource` on refresh, RFC 8707 says policy may limit it.

## Use It When

* You define API scopes and need to know what an AS may do with a request.
* You debug a token with the wrong scope, wrong audience, or a 403.

## Don't Confuse With

* Audience. `scope` names the access, and `resource` and `aud` identify the API. Scope alone is not an audience restriction.
* Consent. The RFCs do not define a consent screen or store. It is one way an AS reaches a decision.
