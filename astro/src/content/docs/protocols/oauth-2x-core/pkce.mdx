Every authorization code flow should use PKCE (Proof Key for Code Exchange), for public and confidential clients alike. RFC 9700 section 2.1.1 says public clients must use it and recommends it for confidential clients. Duende IdentityServer requires it by default through the `RequirePkce` client setting. PKCE binds the authorization code to a secret the app keeps, so a stolen code cannot be redeemed without it.

In the flow, the app sends the user to the authorization server (AS) to sign in and gets back a code, then redeems the code together with the secret.

## Why PKCE Exists

The authorization code travels through the browser, where another party could copy it. If that party could redeem the code, it would get the user's tokens. PKCE closes this gap: the app never sees the user's password, and a stolen code cannot be redeemed without the `code_verifier` that only the app holds. The same flow is the basis of [OpenID Connect](/protocols/openid-connect/openid-connect.mdx) sign-in.

## Authorization Code Flow with PKCE Step by Step

### 1. App creates a verifier and a challenge

The app makes a random secret, the `code_verifier`, and keeps it. It then hashes the verifier into the `code_challenge`. Only the challenge goes through the browser, and the app holds on to the verifier until it redeems the code. RFC 7636 section 4.1 recommends 32 random octets, base64url-encoded to 43 characters, and allows 43 to 128 characters. With `plain`, the challenge is the verifier itself, so anyone who reads the request learns it. Use `S256`.

```text
code_verifier=sbcynbuw4zps1MB2D2VvdSrGYsE659Tt_Gw4nq5hE2Y
code_challenge=6l2xfUivkOjGCWNA7jxKJwO0nk47P3RWI37ll2yRV_k
code_challenge_method=S256
```

<Cite k="pkceChal" />

### 2. App redirects the browser to authorize

The user clicks sign in, and the app answers with a redirect. The browser makes the next request to the AS. That is why anything in the URL is visible to the browser and its history, and why the verifier stays out of it.

<Cite k="authReq" />

### 3. The request carries the challenge

The authorization request carries the challenge. The verifier stays in the app. Note `code_challenge_method=S256`, which tells the AS how to check the verifier later. The `state` value is the app's own check for the callback in step 5.

```http
GET /connect/authorize
  ?client_id=budget&response_type=code
  &redirect_uri=https%3A%2F%2Fbudget.example%2Fcallback
  &scope=openid%20orders&state=kD8YIYundxnaQNpG
  &code_challenge=6l2xfUivkOjGCWNA7jxKJwO0nk47P3RWI37ll2yRV_k
  &code_challenge_method=S256
```

<Cite k="pkceReq" />

### 4. The user signs in at the server

The browser shows the AS sign-in page, and the user types credentials there. The AS also asks for consent if it needs to. The app is not part of this exchange and never sees the password.

<Cite k="grantCode" />

### 5. The server redirects back with a code

The browser then requests the callback URL (`GET /callback`), so the second request on the wire is the browser's hop to the app. Compare `state` with the value the app sent in step 3 before you accept the code.

```http
HTTP/1.1 302 Found
Location: https://budget.example/callback?code=IGjRC6elLNFTRjC1gpc_Qlr1&state=kD8YIYundxnaQNpG

GET /callback?code=IGjRC6elLNFTRjC1gpc_Qlr1&state=kD8YIYundxnaQNpG
Host: budget.example
```

<Cite k="authResp" />

### 6. App redeems the code with the verifier

Now the app sends the verifier it kept in step 1. The AS hashes it with S256 and compares the result with the challenge it stored in step 3. A match shows the caller holds the verifier from the request that started this sign-in, which ties the token request to that authorization request (RFC 7636 sections 3 and 4.6). It does not authenticate a public client. The sample uses a confidential client, so it also sends a Basic header. A public client sends `client_id` and no secret. PKCE does not replace client authentication, so a confidential client still authenticates at the token endpoint (RFC 6749 section 4.1.3).

```http
POST /connect/token
Authorization: Basic <base64(client_id:client_secret)>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=IGjRC6elLNFTRjC1gpc_Qlr1
&redirect_uri=https%3A%2F%2Fbudget.example%2Fcallback
&code_verifier=sbcynbuw4zps1MB2D2VvdSrGYsE659Tt_Gw4nq5hE2Y
```

<Cite k="pkceCheck" />

### 7. The server returns tokens to the app

The AS answers on the back channel, so the tokens never travel in a redirect URL. A server-side app keeps them on the server. A browser-based app still receives them in the browser. The app now has what it needs to call APIs, as described in [access token vs ID token vs refresh token](/protocols/basics/token-types.mdx).

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Pragma: no-cache

{"access_token":"eyJ...","id_token":"eyJ...",
 "token_type":"Bearer","expires_in":3600}
```

<Cite k="rfc6749_5_1" />

## Limits of PKCE

An attacker who can change the `code_challenge` in the victim's authorization request can still inject a stolen code into their own session. PKCE does not stop that (RFC 9700 section 4.5.4). Protect the authorization response from leaking as well.

For the difference from the implicit grant, where tokens come back through the browser, see [Choose the Right OAuth Flow](/protocols/basics/which-oauth-flow.mdx). The `state` parameter ties the callback to the browser session and is not a substitute for the `code_verifier`.
