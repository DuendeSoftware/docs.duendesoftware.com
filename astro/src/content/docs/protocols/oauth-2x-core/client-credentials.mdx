A confidential client authenticates at the token endpoint with its own credentials and receives an access token for itself. No user takes part in the request. It then calls an API with that token.

## Why It Exists

A scheduled job needs to call an API as the service, not as a person. There is no user to redirect to a sign-in page and no consent to ask for, so the job proves who it is with its own credentials. After this page you can follow that path and see which checks the authorization server (AS) and the API make when a scope, a client type, or an audience does not fit.

## How It Works

Steps 1 to 4 are the normal path. Steps 5, 6, and 7 are independent branches for what happens when a scope is narrowed, a public client tries the grant, or a token expires.

## Step by Step

### 1. The worker authenticates and asks for a token

The worker is a confidential client, so it can keep a secret and sends it in the Basic header. The Basic value is the RFC 6749 example, the encoding of `s6BhdRkqt3:gX1fBat3bV`. `scope` is optional, and this request asks for `inventory.read` and `inventory.admin` so step 5 can show scope narrowing. If `scope` is omitted, the AS must either apply a pre-defined default or fail the request. The `resource` parameter names the target API, and the AS accepts values at its own discretion.

```http
POST /connect/token HTTP/1.1
Host: idsrv.example
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=inventory.read%20inventory.admin
&resource=https%3A%2F%2Finventory.example
```

<Cite k="cc" />

### 2. The server authenticates and issues the token

The AS checks the credentials, then issues a token for the client itself. `expires_in` is recommended, not required. The token may be a JWT (RFC 9068) or opaque, and the client does not inspect it.

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{"access_token":"2YotnFZFEjr1zCsicMWpAA",
 "token_type":"Bearer","expires_in":300}
```

<Cite k="rfc6749_5_1" />

### 3. The worker calls the API with the token

The worker puts the token in the `Authorization` header. The API now has to establish two things before it serves the request: that the token is genuine, and that it was meant for this API. The next step lists those checks.

```http
GET /stock/SKU-42 HTTP/1.1
Host: inventory.example
Authorization: Bearer 2YotnFZFEjr1zCsicMWpAA
```

<Cite k="bearer" />

### 4. The API validates the token

The API does not trust the request because it arrived. It checks the signature, the issuer (`iss`), the audience (`aud`, the API the token was issued for), and the expiry (`exp`). It also checks `typ`, a header that tells it this is an access token. A wrong `aud` gets a 401. Whether this client may read `SKU-42` is the API's own policy.

```text
If the token is an RFC 9068 JWT:
  MUST: typ, iss, aud, signature, exp
  SHOULD: scope, with other context
  client_id allowed for SKU-42: local policy
A failed check, such as a wrong aud:
  HTTP/1.1 401 Unauthorized
  WWW-Authenticate: Bearer error="invalid_token"
```

<Cite k="atTyp" />

### 5. If the requested scope is not granted

This is a failure branch. The AS decides what it grants. Compare the `scope` in the response with the one the worker asked for. If they differ, the AS narrowed the request.

```text
Request had scope=inventory.read inventory.admin. Either:
  HTTP/1.1 200 OK
  {"access_token":"...","token_type":"Bearer",
   "scope":"inventory.read"}
or:
  HTTP/1.1 400 Bad Request
  {"error":"invalid_scope"}
```

<Cite k="rfc6749_3_3" />

### 6. If a public client tries the grant

This is a failure branch. A single-page app cannot keep a secret, so it has no credentials to send. The AS refuses the request. If the client authenticates but is not permitted the grant, it gets `unauthorized_client`, and after a failed Basic attempt it gets 401 with `WWW-Authenticate`.

```text
Response to a public client (single-page-app)
that sent no client authentication:
HTTP/1.1 400 Bad Request
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{"error":"invalid_client"}
```

<Cite k="invClient" />

### 7. If the token expires, ask again

Access tokens expire, so a long-running worker sees a 401 with `invalid_token` from the API one day. With no refresh token, the worker repeats the request from step 1: the same Basic header, the same `grant_type=client_credentials`, the same `scope`. It then retries the API call with the new token. RFC 6750 section 3.1 says the client may request a new access token and retry. The spec has no sentence tying that to this grant, so the repeat request is an inference from the missing refresh token.

<Cite k="bearerErr" />

## Notes

If the AS supports it, the client may also authenticate with the body parameters client_id and client_secret, which RFC 6749 section 2.3.1 marks NOT RECOMMENDED. The client must not use more than one authentication method per request (section 2.3). An AS that supports password authentication must protect its endpoint against brute force attacks.

Audience restriction is a SHOULD: the AS should restrict the token to the resource named in the `resource` parameter (RFC 8707 section 2 and RFC 9700 section 2.3). A resource server must still check that the token was meant for it.

RFC 9068 section 5 requires a distinct aud per resource, and says that if the AS uses the client_id as the sub value for client credentials tokens, it should prevent clients from registering an arbitrary client_id, because a malicious client could then choose the sub of a high-privilege resource owner.

Advanced: two descriptions of the resource owner. RFC 6749 section 4.4 also allows the client to act for a resource owner arranged beforehand with the AS. RFC 9068 section 2.2 describes grants where no resource owner is involved, such as the client credentials grant. The two texts differ, and you do not need to resolve this to use the grant.

## Use It When

* A backend service or job calls an API as itself.
* No user's data or consent is part of the request.

## Don't Confuse With

* The [authorization code flow with PKCE](/protocols/oauth-2x-core/pkce.mdx), where a user authorizes and the token carries that user's delegated access.
* Refresh tokens. This grant should not return one.
