The API sends the presented token to the authorization server's introspection endpoint and gets back its current state. Only an active of false means inactive. Everything else is optional metadata.

## Why It Exists

An API that receives a reference (opaque) token cannot read it, and an API that receives a JWT may still want to know whether it has been revoked. Introspection lets the API ask the authorization server (AS) for the token's current state without knowing its format. The API still decides what to allow. After reading, you can tell what the AS answer means and what the API must still check itself.

The actors are the client that holds the token, the API (the resource server, RS) that receives it, and the AS that issued it.

## How It Works

Steps 1 and 2 are the normal start. Steps 3 and 4 are alternative responses to the same introspection request, and the AS sends one of them. Steps 5 and 6 are about what the API does next.

## Step by Step

### 1. The client presents the token to the API

The client sends the token without reading it. To the client the token is opaque. The contents of tokens are opaque to clients (RFC 7662 section 1). It may be a reference value or a JWT, and introspection gives the API the token's state either way.

```http
GET /orders/42 HTTP/1.1
Host: api.example
Authorization: Bearer mF_9.B5f-4.1JqM
```

<Cite k="bearer" />

### 2. The API sends an introspection request

The API, not the client, calls the AS. The AS must require some form of authorization for this call, because the answer can reveal data about a token. Compare the `Authorization` header with step 1: this one is the API's own credential, not the client's token. Bad credentials get HTTP 401, as at the token endpoint. If the hint does not find the token, the AS must search all its token types.

```http
POST /introspect HTTP/1.1
Host: server.example.com
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

token=mF_9.B5f-4.1JqM&token_type_hint=access_token
```

<Cite k="rfc7662_2_1" />

### 3. Alternative: inactive token, active false

This is one possible response. A token that is unknown, expired, revoked, or not allowed gets a normal `200`, not an HTTP error, because the question was answered. Only `active` is returned. The API then answers its own client with `401` and `invalid_token`. That 401 is the API's own behavior (RFC 6750 section 3.1), not part of RFC 7662.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "active": false }
```

<Cite k="rfc7662_2_2" />

### 4. Alternative: active token returns metadata

This is the other possible response. The AS says the token is usable and adds what it knows. Look at `aud`, `exp` and `scope`, because step 5 depends on them.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "active": true,
  "client_id": "budget-app",
  "sub": "alice", "scope": "orders.read",
  "aud": "https://api.example",
  "exp": 1893456000 }
```

<Cite k="rfc7662_2_2" />

### 5. The API treats active as input to policy

Without a profile, `aud`, `exp` and `scope` are optional response members. That does not make them optional for your API. This example API requires `active`, an `aud` that contains its own identifier, an `exp` in the future, and the `orders.read` scope. If the response lacks a field the API needs, the API cannot establish that condition, so it denies access. The `401` `invalid_token` and `403` `insufficient_scope` answers go from the API to the client (RFC 6750 section 3.1). The checks below are guidance from this page, not RFC 7662 requirements.

```text
require active === true
aud contains https://api.example
exp > now
scope contains orders.read
token fails -> 401 invalid_token
privilege missing -> 403 insufficient_scope
```

<Cite k="bearerErr" />

### 6. The API chooses between caching and fresh calls

A longer cache lowers load but leaves a window where a revoked token is still accepted. Highly sensitive deployments can disable caching.

<Cite k="rfc7662_4" />

## Notes

If the AS cannot be reached, or the response is malformed or fails the TLS server certificate check, the API has no trustworthy state. RFC 7662 gives no rule for an unreachable endpoint (the certificate check is a MUST, section 4). Denying access, with a 401 `invalid_token` or a 503, is guidance from this page, not from the RFC.

The AS decides what `active` means (RFC 7662 section 2.2). The RFC lists checks the AS must run, including, if the token can be used only at certain APIs, whether it can be used at the calling API (section 4). Which checks apply is up to the AS. A foreign `aud` on an active response suggests the AS did not apply the section 4 audience check. RFC 9068 section 4 makes the `aud` check a MUST only for JWT access tokens.

A single piece of software acting as both client and protected resource may reuse the same credentials at the token and introspection endpoints. The AS may demand separate ones (section 4).

RFC 7662 describes the protected resource as the caller.

## Use It When

* You want the AS's current view of a token, including revocation, instead of checking it locally.
* The API receives tokens whose format it cannot or should not parse.

## Don't Confuse With

* Local JWT validation (RFC 9068, see [access token validation](/protocols/tokens/access-token-validation.mdx)). It needs no call to the AS, but cannot see revocation on its own.
* Token revocation, which is how a client tells the AS to invalidate a token (see [token revocation](/protocols/tokens/token-revocation.mdx)). Introspection only reads state.
