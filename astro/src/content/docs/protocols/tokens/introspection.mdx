The API sends the presented token to the authorization server's (AS) introspection endpoint and gets back its current state. Only `active` is required in the response. Everything else is optional metadata. The API still decides what to allow.

IdentityServer hosts the introspection endpoint. On the API side, an ASP.NET Core API validates reference tokens by introspection through the OAuth 2.0 introspection handler, authenticating with its own API resource credential.

The actors are the client that holds the token, the API (the resource server, RS) that receives it, and the AS that issued it.

## Why Token Introspection Exists

An API that receives a reference (opaque) token can't read it, so it can't check it locally. An API that receives a JWT may still want to know whether it has been revoked, which local validation can't show. Introspection lets the API ask the AS for the token's current state without knowing its format. [Validating JWT Access Tokens](/protocols/tokens/access-token-validation.mdx) needs no call to the AS but can't see revocation on its own. Introspection only reads state. A client tells the AS to invalidate a token through [Token Revocation](/protocols/tokens/token-revocation.mdx).

## How Token Introspection Works

Steps 1 and 2 are the normal start. Steps 3 and 4 are alternative responses to the same introspection request, and the AS sends one of them. Steps 5 and 6 are about what the API does next.

## Token Introspection Step by Step

### 1. The client presents the token to the API

The client sends the token without reading it, because token contents are opaque to clients (RFC 7662 section 1). It may be a reference value or a JWT, and introspection gives the API the token's state either way.

```http
GET /orders/42 HTTP/1.1
Host: api.example
Authorization: Bearer mF_9.B5f-4.1JqM
```

<Cite k="bearer" />

### 2. The API sends an introspection request

The API calls the AS itself. The AS must require some form of authorization for this call, because the answer can reveal data about a token. The `Authorization` header here is the API's own credential. The client's token from step 1 goes in the body. Bad credentials get HTTP 401, as at the token endpoint. If the hint does not find the token, the AS must search all its token types.

```http
POST /introspect HTTP/1.1
Host: server.example.com
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <base64(client_id:client_secret)>

token=mF_9.B5f-4.1JqM&token_type_hint=access_token
```

<Cite k="rfc7662_2_1" />

### 3. Alternative: inactive token, active false

A token that is unknown, expired, revoked, or not allowed still gets a `200`, because the question was answered. Only `active` is returned. The API then answers its own client with `401` and `invalid_token`. That 401 comes from RFC 6750 section 3.1. RFC 7662 doesn't define it.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "active": false }
```

<Cite k="rfc7662_2_2" />

### 4. Alternative: active token returns metadata

The AS says the token is usable and adds what it knows. Step 5 depends on `aud`, `exp` and `scope`.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "active": true,
  "client_id": "budget-app",
  "sub": "alice", "scope": "orders.read",
  "aud": "https://api.example",
  "exp": 1893456000 }
```

<Cite k="rfc7662_2_2" />

### 5. The API treats active as input to policy

Without a profile, `aud`, `exp` and `scope` are optional response members. That does not make them optional for your API. This example API requires `active`, an `aud` that contains its own identifier, an `exp` in the future, and the `orders.read` scope. If the response lacks a field the API needs, the API cannot establish that condition, so it denies access. The `401` `invalid_token` and `403` `insufficient_scope` answers go from the API to the client (RFC 6750 section 3.1). The checks below are guidance from this page, not RFC 7662 requirements. Those checks are:

```text
require active === true
aud contains https://api.example
exp > now
scope contains orders.read
token fails -> 401 invalid_token
privilege missing -> 403 insufficient_scope
```

<Cite k="bearerErr" />

### 6. The API chooses between caching and fresh calls

The API may cache the response. A longer cache lowers load but leaves a window where a revoked token is still accepted. If the response has `exp`, the API must not cache it beyond that time. Without `exp` the spec sets no upper limit. Highly sensitive deployments can disable caching.

<Cite k="rfc7662_4" />

## When the AS Is Unreachable

If the AS can't be reached, or the response is malformed or fails the TLS server certificate check, the API has no trustworthy state. RFC 7662 gives no rule for an unreachable endpoint, although the certificate check is a must (section 4). Denying access, with a 401 `invalid_token` or a 503, is our recommendation. The RFC doesn't say.

## What Active Means

The AS decides what `active` means (RFC 7662 section 2.2). The RFC lists checks the AS must run, including, if the token can be used only at certain APIs, whether it can be used at the calling API (section 4). Which checks apply is up to the AS. A foreign `aud` on an active response suggests the AS did not apply the section 4 audience check. RFC 9068 section 4 makes the `aud` check a must only for JWT access tokens.

A single piece of software acting as both client and protected resource may reuse the same credentials at the token and introspection endpoints. The AS may demand separate ones (section 4).
