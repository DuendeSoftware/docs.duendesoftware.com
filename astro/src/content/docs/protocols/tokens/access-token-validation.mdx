An API that receives a JWT access token (RFC 9068) checks the header, the signature, and the `iss`, `aud` and `exp` claims, then applies its own authorization. A valid token is not a permitted request.

## Why It Exists

Picture an ASP.NET Core API that receives a bearer token. The token parses fine, so is it safe to serve the call? Not yet. A token can be well-formed and correctly signed and still be meant for a different API, or have expired. RFC 9068 lists the checks the resource server (RS, your API) MUST make, and a token that passes them still does not by itself permit the call. After reading, you can name each check, the claim or header it looks at, and which part is your application's own decision.

Terms used below: the authorization server (AS) issues the token and signs it. `iss` is the issuer that signed the token. `aud` is the audience, the API the token is for. `exp` is the expiry time. `kid` is the ID of the signing key. `typ` is the JWT type in the header.

## How It Works

For an opaque token, which the API cannot read, use [introspection](/protocols/tokens/introspection.mdx) instead of this pipeline. Where an API-specific `aud` comes from is covered by [resource indicators](/protocols/security-hardening/resource-indicators.mdx).

## Step by Step

### 1. The client sends the bearer token

Resource servers MUST support this method. The `eyJ` prefix is how a base64url-encoded JSON header starts. The host and path are examples. The API treats the token as untrusted input until the checks pass.

```http
GET /orders/42 HTTP/1.1
Host: api.example
Authorization: Bearer eyJ...
```

<Cite k="bearer" />

### 2. The API gets the AS's signing keys

The API cannot check a signature without the AS's public key. RFC 9068 section 4 says the AS SHOULD publish its keys and issuer through RFC 8414 metadata, and an OpenID Connect AS MAY use its discovery document instead, so the API reads whichever the AS publishes. The metadata `issuer` must equal the issuer the API is configured for. Caching and refresh are deployment policy.

```http
GET /.well-known/oauth-authorization-server HTTP/1.1
Host: login.example

HTTP/1.1 200 OK
{"issuer": "https://login.example", "jwks_uri": "https://login.example/jwks", ...}
```

<Cite k="asMetaReq" />

### 3. The API checks the JOSE header

The header tells the API how to verify the token. Here is the header and the payload of the example token, decoded. The `typ` check keeps an ID token from being accepted as an access token. The allow-list of algorithms comes from the API's configuration, not from AS metadata, and RFC 8725 says each key is used with exactly one algorithm. `kid` is a hint (OPTIONAL in RFC 7515). When present, it picks the key. When absent, the API tries the compatible keys (practice, not a spec step), because RFC 9068 section 5 says resource servers have to accept signatures made with any published key.

```json
{
  "typ": "at+jwt",
  "alg": "RS256",
  "kid": "2026-01"
}
```

The payload decodes to values the API checks in step 5:

```json
{
  "iss": "https://login.example",
  "aud": "https://api.example",
  "exp": 1893456000,
  "iat": 1893452400,
  "jti": "d7f8c3a2-4b1e-4e9a-8c1d-2f5a6b7c8d9e",
  "sub": "alice",
  "client_id": "budget-app",
  "scope": "orders.read"
}
```

<Cite k="atTyp" />

### 4. The API verifies the signature

RFC 9068 requires that the resource server uses keys provided by the AS. The API verifies the signature over the encoded header and payload with the AS's key, using the algorithm in `alg`. Verification is a computation inside the API, so the arrow is internal.

<Cite k="rfc7515_5_2" />

### 5. The API checks iss, aud and exp

These are the claim checks in RFC 9068 section 4. Compare `iss` in the payload with the issuer the API is configured for, `aud` with the API's own identifier, and `exp` with the API's own clock. In the example above, an API that is not `https://api.example` rejects the token, even with a valid signature. `nbf` is OPTIONAL and not in that list, and RFC 7519 says to reject a token before its `nbf`. RFC 9068 section 4 does not list `iat`, `jti`, `sub` or `client_id` checks, but RFC 8725 section 3.8 still requires validating a `sub` the application relies on.

<Cite k="rfc9068_4" />

### 6. The API applies its own authorization

A valid token is not permission. RFC 9068 says the resource server SHOULD use the authorization claims in the token together with other context, and that how it does this is beyond the profile. Tenant and ownership checks are application policy, and no spec defines them. In ASP.NET Core this is the authorization step, after authentication. The arrow is internal because nothing is sent.

<Cite k="rfc9068_4" />

### 7. The API answers the client

The two status codes match two ASP.NET Core outcomes. `401 Unauthorized` means authentication failed, so the token is not acceptable. `403 Forbidden` means authentication worked but authorization failed, so the caller is known and not allowed. RFC 9068 section 4 says the response to any failed validation MUST include `invalid_token`, and RFC 6750 says the `WWW-Authenticate` header MUST be sent. The 401 status and the `error` attribute are SHOULD, and so is the 403 for insufficient scope (RFC 6750 section 3.1), whose `scope` attribute is a MAY. With no token, the response SHOULD NOT include an error code or other error information. A failed ownership or tenant check is application policy, so its status is the application's choice.

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="orders.read"
```

<Cite k="bearerErr" />

## Notes

The spec gives no order for the checks in this pipeline, and RFC 7515 says order does not matter where steps have no dependencies. The real dependencies are that the API needs the key before it can check the signature, and that it decrypts an encrypted token first. For a nested (encrypted) JWT, `typ` sits in the inner header (RFC 8725 section 3.11), so the `typ` check follows decryption. A token that is encrypted is decrypted with the keys and algorithms the resource server specified at registration.

Not covered: the HTTP 400 `invalid_request` response, DPoP or mTLS binding, and replay checks with `jti`, which RFC 9068 does not require of the resource server.

The AS must use a distinct `aud` for each resource (RFC 9068 section 5). Typing with `typ` is one defence against confusing an ID token with an access token. RFC 8725 notes it may not disambiguate every JWT kind.

## Use It When

* You build or review an API that accepts JWT access tokens.
* You debug a 401 `invalid_token` or a 403 from an API.

## Don't Confuse With

* ID token validation, which a client does under OpenID Connect Core (see [OpenID Connect](/protocols/openid-connect/openid-connect.mdx)). An API must not accept an ID token as an access token, which is what the `typ` check is for.
* Opaque access tokens, which an API checks by [introspection](/protocols/tokens/introspection.mdx), not by this pipeline.
