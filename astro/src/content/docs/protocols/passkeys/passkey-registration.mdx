The relying party sends fresh creation options, the browser enforces the RP ID scope, and the authenticator creates a key pair. The RP validates the response and stores the public key.

## Why It Exists

Registration happens while the account is already known, for example after the user signed in with a password. It gives that account a public-key record the site can use for later sign-in, so no shared secret is stored. After reading this page you can follow one registration and say what the relying party (RP) must check before it stores a credential.

Three terms matter here. The **authenticator** is the device or software that holds the keys, such as a phone or a security key. The **RP ID** is the domain a credential is scoped to, for example `login.contoso.example`. The **challenge** is a random value the RP creates and keeps, so it can check that the response answers this request. The browser sits between the RP and the authenticator and enforces the RP ID scope.

Step 7 is a failure branch, not part of the normal path.

## Step by Step

### 1. The RP sends the creation options

The RP creates a fresh random challenge and keeps it, for example in the server-side session, until the ceremony ends. It should let it expire. The options object is the argument of `create()`, not a message format. How the server hands it to the page is app-defined, and the example shows a JSON form with the byte fields as base64url. `user.id` is an opaque handle of 1 to 64 bytes, without personal data. Notice that `excludeCredentials` is not in this example. It is covered in step 6.

```text
// app-defined JSON from the RP to the page; byte fields are base64url
{"rp":{"id":"login.contoso.example","name":"Contoso"},
 "user":{"id":"oJXyD5OVZQz5OAuO2yJKaw","name":"alice@contoso.example","displayName":"Alice"},
 "challenge":"UvImZaYMEtKJGF2VDuiBNgkWb2sRPReNbA_TkB_yOaE",
 "pubKeyCredParams":[{"type":"public-key","alg":-7}],
 "authenticatorSelection":{"residentKey":"required","userVerification":"required"},
 "attestation":"none"}
```

<Cite k="waSecChallenges" />

### 2. The browser calls create(), checks the RP ID

The page decodes the base64url fields and calls `create()`. Before it asks the authenticator for anything, the browser compares the RP ID with the page's origin. If they do not fit, it throws a `SecurityError` and shows no prompt. This is why a look-alike site cannot register a credential for your RP ID. The call from the browser to the authenticator is local, and WebAuthn defines no front or back channel for it. The RP does not send `clientDataJSON`. The browser builds it. Decode with base64url, not `atob`.

```text
navigator.credentials.create({ publicKey: options })
// RP ID login.contoso.example is the effective domain of https://login.contoso.example
// clientDataJSON, 145 bytes, built by the browser; the authenticator gets its SHA-256 hash
{"type":"webauthn.create","challenge":"UvImZaYMEtKJGF2VDuiBNgkWb2sRPReNbA_TkB_yOaE",
 "origin":"https://login.contoso.example","crossOrigin":false}
```

<Cite k="waCreateMethod" />

### 3. The authenticator verifies the user, makes keys

Here the user makes a gesture at the authenticator, such as a touch, a PIN or a biometric. The authenticator tests user presence, and user verification when the RP required it, then creates a new key pair for this RP ID. A passkey is a discoverable credential, so the authenticator can offer it at sign-in without the RP naming it. The BE flag later shows whether the credential can be synced.

<Cite k="waMakeCredential" />

### 4. The authenticator returns the attestation object

What the RP needs from this object is the credential ID and the public key. Both sit inside `authData`. The private key is never sent to the RP. A synced passkey can still copy the key to the user's other devices through the passkey provider, which WebAuthn Level 3 calls backup eligibility.

The rest is encoding detail. The authenticator picks the attestation format from `attestationFormats`, or its own preference. A self attestation can come back as `packed` even when `none` was requested. The excerpt below is shortened. The real object is 194 bytes of CBOR, with a 164-byte `authData`.

```text
// attestationObject (CBOR), diagnostic notation, excerpt
{"fmt":"none","attStmt":{},"authData":h'<164 bytes>'}
authData rpIdHash 7b8378498cb5e73b1d64f7b3c77659aa28f3727f2aa50208bce13160497e17b4
authData flags 0x45 (UP, UV, AT)   signCount 00000000
authData aaguid 16 zero bytes   credentialId JIoekk6P0K4uGpSSozBfGIy2EJAPnjR_rohtxlB3lew
authData credentialPublicKey COSE_Key: kty 2, alg -7 (ES256), crv 1, x, y
```

<Cite k="waNoneFormat" />

### 5. The browser posts the response to the RP

The page forwards the three values the RP needs. The RP then has what it needs to check the ceremony against the challenge it stored.

```text
// app-defined JSON body from the page to the RP; excerpt, buffers shortened
{"id":"JIoekk6P0K4uGpSSozBfGIy2EJAPnjR_rohtxlB3lew","type":"public-key",
 "response":{
  "clientDataJSON":"eyJ0eXBlIjoid2ViYXV0aG4uY3JlYXRlIiwiY2hhbGxl...",
  "attestationObject":"o2NmbXRkbm9uZWdhdHRTdG10oGhhdXRoRGF0YVik..."}}
```

<Cite k="waAttestationResponse" />

### 6. The RP validates the response and stores it

The RP checks the response against what it stored in step 1, then saves the credential. The origin check is an additional layer in case a faulty authenticator fails to enforce credential scope. With `none`, the RP's policy decides whether the missing attestation is acceptable, and it may register the credential as self attestation.

Storage has two parts. The credential record holds `type`, `id`, `publicKey`, `signCount`, `uvInitialized`, `transports`, `backupEligible` and `backupState`. The RP also links the credential to the account, because the user handle lives on the user account. The RP should pass the user's existing credentials in `excludeCredentials`, so the same authenticator does not register a second credential for that account. It should also fail the ceremony for a credential ID that is already registered for any user (WebAuthn section 7.1).

```text
MUST    type is webauthn.create; challenge equals the one sent; origin is expected
MUST    rpIdHash is SHA-256 of the RP ID; UP set; UV set if required; alg was requested
SHOULD  attestation trustworthy (none: policy decides); credentialId at most 1023 bytes
SHOULD  credentialId not yet registered for any user
store   type, id, publicKey, signCount, uvInitialized, transports, backupEligible, backupState
```

<Cite k="webauthnCredentialRecord" />

### 7. If create() fails: nothing is stored

This is a failure branch. When `create()` rejects, the page has no response to send, so the RP stores no credential. The error name tells you why.

```text
create() rejects; the RP stores no credential record
SecurityError    the RP ID is not valid for the page's origin (no prompt is shown)
NotAllowedError  the user cancelled or did not consent, or no suitable authenticator before the timeout
ConstraintError  residentKey or userVerification is required and no authenticator can meet it (section 5.1.3.1)
```

## Notes

Attestation can be used to track users, so `none` or an anonymized statement avoids identifying information (WebAuthn sections 14.4.1 and 5.1.3). With `none`, the client sets `fmt` to `none` and `attStmt` to an empty map. Attestation describes the authenticator, not the person, and cannot show that a response came from the authenticator the user meant.

The BE flag shows that a credential can be backed up, for example by sync. BS shows the current state. BE is set at creation and does not change. Store both flags, and give each account another authenticator or a recovery process, because a single-device credential does not survive device loss.

Practice, not required by the spec: accept each challenge only once.

## Use It When

* A site lets a user add a passkey (a discoverable WebAuthn credential) to an account.
* You want to see which checks the RP must make before it stores a new credential.

## Don't Confuse With

* [Passkey sign-in](/protocols/passkeys/passkey-signin.mdx), which uses an existing credential to sign a challenge (the assertion flow). It is the next page.
* Passwords with MFA, where a shared secret is typed and sent to the server.
