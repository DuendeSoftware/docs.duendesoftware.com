The client POSTs its authorization request straight to the PAR endpoint, authenticated like a token request, and gets back a short-lived `request_uri`. The browser then carries only `client_id` and `request_uri`.

## Why It Exists

An ordinary authorization request is a long URL in the browser. Its parameters (`scope`, `redirect_uri`, `state`, `code_challenge`) can be read in logs and history, and anyone with access to the browser can change them. A pushed authorization request (PAR, RFC 9126) fixes that by sending the parameters from the client to the authorization server (AS) over a direct, authenticated call. The browser then carries a reference instead. The AS can refuse a bad request before any user interaction.

PAR adds no signed Request Object. A JWT-secured authorization request (JAR) is that signed object, and you can add it later when you need one. See the Notes.

## How It Works

The flow builds on the [authorization code flow with PKCE](/protocols/oauth-2x-core/pkce.mdx). Read that page first if the `code_challenge` below is new to you.

## Step by Step

### 1. Client builds the authorization request

The client builds the same authorization request it would normally put in a browser URL: the response type, scope, redirect URI, `state` and the PKCE challenge. What changes is the next step. Instead of putting these parameters in the browser, the client keeps them and sends them to the AS directly.

<Cite k="parIntro" />

### 2. Client pushes the request to the PAR endpoint

Look at two lines. `Authorization: Basic` is the client authenticating at the PAR endpoint, the same way it would at the token endpoint. The AS knows who is pushing the request. `code_challenge` is the PKCE challenge. PKCE still protects the code redemption later, and client authentication does not replace it. Neither replaces the other.

```http
POST /par HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Authorization: Basic cGF5bWVudHMtYXBwOnMzY3IzdA==

client_id=payments-app&response_type=code&scope=payments.write
&redirect_uri=https%3A%2F%2Fclient.example%2Fcb&state=af12
&code_challenge=6l2xfUivkOjGCWNA7jxKJwO0nk47P3RWI37ll2yRV_k
&code_challenge_method=S256
```

<Cite k="parEndpoint" />

### 3. The server authenticates and validates

The AS authenticates the client, then checks the request as it would at the authorization endpoint. A bad request fails here, before the user sees anything.

```text
Example checks, not a full list:
  client authenticated; no request_uri
  redirect_uri matches a configured URI (*)
  client is authorized for the scope
(*) an AS MAY relax exact matching for authenticated clients
on failure: HTTP 400 + the appropriate error code
 (e.g. invalid_request for a bad redirect_uri), or
HTTP 401 invalid_client after header auth
```

<Cite k="parEndpoint" />

### 4. The server returns a request_uri

The AS stores the request and hands back a reference to it. The `request_uri` is the claim ticket the client gives to the browser next.

The `Cache-Control` header comes from the RFC 9126 example, not from a stated requirement. The urn form is one allowed format. 60 seconds is the example lifetime, and the spec suggests 5 to 600 seconds as typical.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Cache-Control: no-cache, no-store

{"request_uri":
  "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c",
 "expires_in": 60}
```

<Cite k="parResponse" />

### 5. The browser sends only two parameters

The client replaces the browser-visible parameters with a reference. The browser carries only `client_id` and `request_uri`, so there is nothing sensitive to read or edit in the URL.

An attacker could try to swap in a `request_uri` of their own. Clients should use PKCE, a unique `state` or the OIDC `nonce` so a swapped `request_uri` fails (RFC 9126 section 7.5). That is the reason the PKCE challenge from step 2 matters here too.

```http
GET /authorize?client_id=payments-app
 &request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri
 %3A6esc_11ACC5bwc014ltc14eY22c HTTP/1.1
Host: as.example
```

<Cite k="parRequest" />

### 6. The server resolves the reference

The AS looks up the stored request, checks that it belongs to this client and has not expired, and then continues the normal authorization flow, with sign-in and consent. The server must validate the request as it would any other authorization request. Because client policy can change between push and use, the spec recommends checking the request against it again here (section 7.4).

<Cite k="parRequest" />

## Notes

PAR alone creates no signed Request Object. RFC 9126 section 1 points to JAR for clients that need cryptographically confirmed non-repudiation, and section 3 lets a client push a Request Object in the `request` parameter.

A public client can send `client_id` without credentials, but the server must not rely on public client authentication to identify the client (RFC 6749 section 2.3).

The server must accept new redirect URIs in a pushed request only from authenticated clients (RFC 9126 section 7.2).

## Use It When

* You want the request authenticated and validated before the user is involved.
* The parameters are sensitive or too large for a browser URL.

## Don't Confuse With

* JAR, which signs the request as a Request Object. PAR only delivers it and can carry one.
* The token endpoint. PAR uses its client authentication rules but returns a `request_uri`, never tokens.
