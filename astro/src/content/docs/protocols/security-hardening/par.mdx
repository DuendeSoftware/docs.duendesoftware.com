A pushed authorization request (PAR, RFC 9126) means the client POSTs its authorization request straight to the PAR endpoint, authenticated like a token request, and gets back a short-lived `request_uri`. The browser then carries only `client_id` and `request_uri`. PAR adds no signed Request Object. A JWT-secured authorization request (JAR) is that signed object, and PAR can carry one in the `request` parameter.

## Why Pushed Authorization Requests Exist

An ordinary authorization request is a long URL in the browser. Its parameters (`scope`, `redirect_uri`, `state`, `code_challenge`) can be read in logs and history, and anyone with access to the browser can change them. PAR sends the parameters from the client to the authorization server (AS) over a direct, authenticated call, and the browser carries a reference instead. The AS can refuse a bad request before any user interaction. RFC 9126 section 1 points to JAR for clients that need cryptographically confirmed non-repudiation.

## How Pushed Authorization Requests Work

The flow builds on the [Authorization Code Flow with PKCE](/protocols/oauth-2x-core/pkce.mdx), so the request carries a `code_challenge`. The lanes are the client, the user's browser and the AS. Steps 1 to 4 happen between the client and the AS, and steps 5 and 6 are the browser leg.

## Pushed Authorization Requests Step by Step


### 1. Client builds the authorization request

The client builds the same authorization request it would normally put in a browser URL: the response type, scope, redirect URI, `state` and the PKCE challenge. Instead of putting these parameters in the browser, the client keeps them and sends them to the AS directly.

<Cite k="parIntro" />

### 2. Client pushes the request to the PAR endpoint

`Authorization: Basic` is the client authenticating at the PAR endpoint, the same way it would at the token endpoint, so the AS knows who is pushing the request. `code_challenge` is the PKCE challenge. PKCE still protects the code redemption later, and client authentication doesn't replace it. `request_uri` must not be sent in this request. A public client can send `client_id` without credentials, but the server must not rely on public client authentication to identify the client (RFC 6749 section 2.3).

```http
POST /par HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <base64(client_id:client_secret)>

client_id=payments-app&response_type=code&scope=payments.write
&redirect_uri=https%3A%2F%2Fclient.example%2Fcb&state=af12
&code_challenge=6l2xfUivkOjGCWNA7jxKJwO0nk47P3RWI37ll2yRV_k
&code_challenge_method=S256
```

<Cite k="parEndpoint" />

### 3. The server authenticates and validates

The AS authenticates the client, rejects any `request_uri`, then checks the request as it would at the authorization endpoint. A bad request fails here, before the user sees anything. The server must accept new redirect URIs in a pushed request only from authenticated clients (RFC 9126 section 7.2).

```text
Example checks, not a full list:
  client authenticated; no request_uri
  redirect_uri matches a configured URI (*)
  client is authorized for the scope
(*) an AS MAY relax exact matching for authenticated clients
on failure: HTTP 400 + the appropriate error code
 (e.g. invalid_request for a bad redirect_uri), or
HTTP 401 invalid_client after header auth
```

<Cite k="parEndpoint" />

### 4. The server returns a request_uri

The AS stores the request and hands back a reference to it. The `request_uri` is the reference the client gives to the browser next.

On success the response is `201`. The server picks the format and lifetime of the `request_uri`. The value needs an unguessable random part and is bound to the client. The `Cache-Control` header comes from the RFC 9126 example and isn't a stated requirement. The urn form is one allowed format. 60 seconds is the example lifetime, and the spec suggests 5 to 600 seconds as typical.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Cache-Control: no-cache, no-store

{"request_uri":
  "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c",
 "expires_in": 60}
```

<Cite k="parResponse" />

### 5. The browser sends only two parameters

The client replaces the browser-visible parameters with a reference. The browser carries only `client_id` and `request_uri`, so there is nothing sensitive to read or edit in the URL.

The client must use a `request_uri` once, and the server must reject an expired one. An attacker could try to swap in a `request_uri` of their own. Clients should use PKCE, a unique `state` or the OIDC `nonce` so a swapped `request_uri` fails (RFC 9126 section 7.5). That is why the PKCE challenge from step 2 matters here too.

```http
GET /authorize?client_id=payments-app
 &request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri
 %3A6esc_11ACC5bwc014ltc14eY22c HTTP/1.1
Host: as.example
```

<Cite k="parRequest" />

### 6. The server resolves the reference

The AS looks up the stored request, checks that it belongs to this client and has not expired, and then continues the normal authorization flow, with sign-in and consent. Because client policy can change between push and use, the spec recommends checking the request against it again here (section 7.4).
