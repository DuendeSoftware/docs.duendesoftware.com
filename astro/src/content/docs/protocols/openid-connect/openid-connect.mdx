OpenID Connect (OIDC) adds authentication to the OAuth authorization code flow. The client asks for the `openid` scope and receives an ID token about the user, for the client, next to an access token for APIs. The ID token is a signed JWT. The client validates it, and only then treats the user as signed in. The access token is for APIs, and the ID token is not. Plain OAuth 2.0 authorizes access and defines no user identity.

In OIDC, the relying party (RP) is the app that wants to know who the user is. The OpenID provider (OP) is the server that signs the user in and issues tokens. IdentityServer is the OP. You register each app as a client in IdentityServer, and an ASP.NET Core app acts as the RP through its OpenID Connect handler.

## Why OpenID Connect Exists

OAuth lets a client call an API on a user's behalf, but it gives no standard proof of who signed in. Apps that needed one built their own on top of OAuth, and each did it differently. OIDC adds the ID token and the checks on it, so every client signs users in the same way.

Three values protect the exchange:

* **PKCE** (Proof Key for Code Exchange) ties the code to the RP that asked for it. See [Authorization Code Flow with PKCE](/protocols/oauth-2x-core/pkce.mdx).
* **`state`** lets the RP match the response to its own request.
* **`nonce`** ties the ID token to this sign-in, so an old ID token can't be replayed.

## OpenID Connect Sign-In Step by Step

### 1. RP sends the authentication request

This is an OAuth authorization request that also asks for the user to be authenticated. The browser carries it to the OP. `redirect_uri` must exactly match a pre-registered value (Core section 3.1.2.1). `scope` includes `openid`, which is what makes this an OIDC request. `state`, `nonce` and the PKCE challenge are generated by the RP and kept for later. The values in angle brackets are placeholders and must be unguessable. PKCE is not an OIDC Core requirement. RFC 9700 section 2.1.1 says public clients must use it and confidential clients should. Confidential OIDC clients may use `nonce` instead of PKCE, with extra precautions. In the code flow `nonce` is optional, but if the RP sent one, the `nonce` claim must be present and match.

```http
HTTP/1.1 302 Found
Location: https://identity.example/authorize?
  response_type=code&client_id=budget
  &scope=openid%20profile%20orders
  &redirect_uri=https%3A%2F%2Fbudget.example%2Fcallback
  &state=af0ifjsldkj&nonce=<random nonce>
  &code_challenge=<S256 of code verifier>
  &code_challenge_method=S256
```

<Cite k="oidcReq" />

### 2. OP authenticates the user and redirects back

The OP shows its own sign-in page, so the RP never sees the user's password. How the OP authenticates the user (password, session cookie, other) is outside the spec (Core section 3.1.2.3). Compare `state` in the redirect with the one the RP sent, because the RP must check that they match. The `iss` parameter is from RFC 9207, not OIDC Core, and lets the RP check which OP answered.

```http
HTTP/1.1 302 Found
Location: https://budget.example/callback?
  code=SplxlOBeZQQYbYS6WxSbIA
  &state=af0ifjsldkj
  &iss=https%3A%2F%2Fidentity.example
```

<Cite k="oidcAuthResp" />

### 3. RP redeems the code with its verifier

The RP calls the token endpoint directly from its server and sends the original `code_verifier`. The OP checks it against the `code_challenge` from step 1, so a stolen code is useless without the verifier. A confidential client authenticates to the token endpoint instead of sending only `client_id` (Core section 3.1.3.1). PKCE and client authentication protect different things, so a confidential client can use both.

```http
POST /token HTTP/1.1
Host: identity.example
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fbudget.example%2Fcallback
&client_id=budget&code_verifier=<code verifier>
```

<Cite k="oidcTokenReq" />

### 4. OP returns ID token and access token

The OP issues two tokens for two audiences. The `id_token` is for the RP and describes the sign-in. The `access_token` is for APIs. The access token format is unspecified by OIDC, so the example uses a placeholder. A refresh token is optional and not shown.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Pragma: no-cache

{"access_token":"shared-token...","id_token":"eyJ...",
 "token_type":"Bearer","expires_in":3600}
```

<Cite k="oidcTokenResp" />

### 5. RP validates the ID token

The RP treats the user as signed in only after these checks pass. Compare each claim with what the RP knows. `iss` must be the OP the RP expects. `aud` must contain the RP's own `client_id`, which is `budget` here. `exp` must be in the future. If the RP sent a `nonce` in step 1, the `nonce` claim must equal it. That match ties this ID token to this sign-in, so an old ID token cannot be replayed. The RP also verifies the signature. In the code flow, TLS validation of the token endpoint may replace the signature check. `alg` should be `RS256` or the algorithm the client registered, and `alg` `none` is allowed only if the client asked for it at registration. Sessions are app behavior, and the spec defines only the checks. The timestamps in the example are the spec's sample values, and a real token's `exp` lies in the future.

```json
{
  "iss": "https://identity.example",
  "sub": "24400320",
  "aud": "budget",
  "nonce": "<same nonce as step 1>",
  "exp": 1311281970,
  "iat": 1311280970
}
```

<Cite k="idVal" />

### 6. RP calls the API with the access token

In the normal call below, the RP sends `shared-token...`, the access token, to the API. If the RP sent the ID token instead, its `aud` would be `budget`, the RP's client ID, and a resource server must refuse tokens not meant for it (RFC 9700 section 2.3).

```http
GET /orders HTTP/1.1
Host: api.example
Authorization: Bearer shared-token...
```

<Cite k="bcpAud" />

### 7. Optional UserInfo call for more claims

The RP uses the access token to ask the OP for more claims about the user. The RP checks that `sub` in the response equals the ID token `sub`, and must not use the response if they differ (Core section 5.3.2). The `profile` scope claims are returned here. Without the `openid` scope the behavior is entirely unspecified (Core section 3.1.2.1).

```http
GET /userinfo HTTP/1.1
Host: identity.example
Authorization: Bearer shared-token...

HTTP/1.1 200 OK
Content-Type: application/json

{"sub":"24400320","name":"Jane Doe"}
```
