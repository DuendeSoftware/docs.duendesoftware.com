The relying party (RP) fetches the OpenID provider's (OP) metadata from `/.well-known/openid-configuration` and accepts it only if the `issuer` in it matches the issuer URL it fetched from. It then takes signing keys from the `jwks_uri` named in that metadata and picks the key by the token's `kid`. When it sees a `kid` it doesn't know, it refetches the JWK Set. The RP never takes keys from the token itself.

Terms used on this page: the **issuer** is the OP's identifier, an `https` URL. The **discovery document** is the JSON metadata the OP publishes under that URL. A **JWK Set** (JWKS) is the list of the OP's public keys. The **`kid`** (key ID) is a label in a token's header that says which key in the set signed it. In IdentityServer, the OP publishes the discovery document and JWK Set and rotates keys. An ASP.NET Core client or API reads them through its `Authority` setting. OAuth 2.0 Authorization Server Metadata (RFC 8414) uses `/.well-known/oauth-authorization-server` instead.

## Why OpenID Connect Discovery Exists

A client that signs users in through an [OpenID Connect](/protocols/openid-connect/openid-connect.mdx) OP needs to find the OP's endpoints and the public keys that sign its tokens. Hardcoding them breaks when the OP changes a URL or rotates a key. A token's own header can't be trusted to say where its keys are, because an attacker could point it at their own keys. So the RP reads the locations from the issuer's metadata and refetches the keys when the OP rotates them.

## Discovery and Key Rotation Step by Step

### 1. The RP fetches the discovery document

The issuer URL comes from the RP's configuration. In ASP.NET Core this is the `Authority` setting of the OpenID Connect handler. If the issuer URL has a path, a terminating `/` is removed before you append `/.well-known/openid-configuration`.

```http
GET /.well-known/openid-configuration HTTP/1.1
Host: identity.example
Accept: application/json
```

<Cite k="discoveryGet" />

### 2. The OP returns metadata, RP checks issuer

The RP compares the `issuer` value in the JSON with the issuer URL it fetched from. If they differ, the RP must not use the data and must abort the operations that need it. This stops a response from one server from describing another. The RP can also learn the issuer through WebFinger (Discovery section 2), an optional lookup from a user identifier such as an email address to an issuer URL. Most applications skip it and configure the issuer.

The JSON is an excerpt. Discovery section 3 requires `issuer`, `authorization_endpoint`, `jwks_uri`, `response_types_supported`, `subject_types_supported` and `id_token_signing_alg_values_supported`. It also requires `token_endpoint` unless only the Implicit Flow is used. The `issuer` must use `https` and have no query or fragment.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "issuer": "https://identity.example",
  "jwks_uri": "https://identity.example/jwks",
  "id_token_signing_alg_values_supported": ["RS256"],
  ... }
```

<Cite k="discoveryVal" />

### 3. The RP fetches the jwks_uri

The RP gets the key location from the validated metadata and never from the ID token. Core section 2 says ID Tokens should not use the `jku`, `x5u`, `x5c` or `jwk` header fields, and that key references are communicated in advance through discovery. RFC 8725 section 3.10 warns that blindly following a `jku` URL can lead to server-side request forgery. The `jwks_uri` must use `https`.

```http
GET /jwks HTTP/1.1
Host: identity.example
Accept: application/json
```

<Cite k="discovery" />

### 4. The OP returns the JWK Set

Read the response in this order. `keys` is the list. Each entry is one public key. `kid` is its label, `kty` is the key type, and `n` and `e` are the public values of an RSA key. The RP holds only public keys, so it can verify signatures but never create them. The RP keeps the set to verify later tokens.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "keys": [ { "kty": "RSA", "use": "sig", "kid": "2026-01", "alg": "RS256",
  "n": "05TZKItUoute6BJciKIxZfxYQa2Qw...(2048-bit modulus, shortened)...ciMRjani5w",
  "e": "AQAB" } ] }
```

An RSA key carries `kty`, `n` and `e` (RFC 7518 section 6.3.1). `AQAB` is the exponent 65537. The real `n` here is a 2048-bit modulus, and RS256 needs 2048 bits or more (RFC 7518 section 3.3). `kty` must be present (RFC 7517 section 4.1). `use` and `alg` are optional (RFC 7517 sections 4.2 and 4.4), but `use` becomes required for every key when the set publishes both signing and encryption keys. The `kid` member is optional, but when the set has several keys the signer must put `kid` in the token's JOSE header (Core section 10.1). How long the RP caches the set is an implementation choice.

<Cite k="jwaRsaPub" />

### 5. RP selects a key by kid, validates

The ID token header names the key, so the RP looks up the matching `kid` in its cached set. The RP checks that:

* The OP's issuer is the configured one.
* The metadata passed the issuer check from step 2.
* The keys came from the `jwks_uri` in that metadata.
* The token's `kid` matches a key in the set.
* The signature verifies with that key, and the claims (`iss`, `aud`, `exp`, and `nonce` if the RP sent one) are valid.

A `kid` only says which key to try. It proves nothing. The `alg` should be the default RS256 or the registered `id_token_signed_response_alg` (Core section 3.1.3.7). RFC 8725 section 3.1 requires libraries to let the caller restrict algorithms and to use each key with one algorithm. A token whose `alg` the application does not accept should be treated as invalid even if the signature verifies (RFC 7515 section 5.2). TLS validation may replace the signature check when the ID token arrives directly from the token endpoint.

An RP validating an ID token checks that the token was issued for it, using its own `client_id` as `aud`. An API validating an access token expects an `aud` that names the API. See [Validating JWT Access Tokens](/protocols/tokens/access-token-validation.mdx) for that side.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{ "access_token": "SlAV32hkKG", "token_type": "Bearer", "id_token": "eyJ..." }
# id_token header (decoded): { "alg": "RS256", "kid": "2026-01" }
```

<Cite k="idVal" />

### 6. Rotation: an unfamiliar kid triggers a refetch

The OP replaces its signing key from time to time. The OP adds the new key to its JWK Set and starts signing with it. The next token carries `kid` `2026-10`, which the RP's cache does not have. That unfamiliar `kid` is the signal to refetch the set from `jwks_uri`.

Core section 10.1.1 says the signer adds new keys and starts using one at its discretion. The signing key must be in the set (section 10.1), but publishing it early is not required. Duende IdentityServer announces a new key in discovery before it signs with it, following its own key-management settings. OIDC doesn't require this. It's Duende product behavior. The OP should keep recently decommissioned keys in the set for a reasonable period, so tokens signed shortly before the change still verify. The specs set no limit on how often the RP refetches.

```text
# request and response
GET /jwks HTTP/1.1
Host: identity.example

HTTP/1.1 200 OK
{ "keys": [ { "kid": "2026-01", ... }, { "kid": "2026-10", ... } ] }
```

<Cite k="oidcRotation" />

### 7. If no key matches or signature fails

This is an alternative outcome. If `kid` is still unknown after the refetch, or the signature fails on a known key, the RP rejects the token. A JWS whose signature does not validate is invalid (RFC 7515 section 5.2). The client must use the keys provided by the issuer (Core section 3.1.3.7), and RFC 8725 section 3.8 requires rejecting a JWT whose keys do not belong to its issuer.

Not refetching after a bad signature on a known key, and limiting refetches for random `kid` values, are policy choices. `kid` values only should be distinct within one JWK Set (RFC 7517 section 4.5).
